# 设计：柏讯模块体检

## Context

见 proposal.md——动机不赘述。体检对象是两根共 68 条 spec（finddata 根 `openspec/specs/wire-*` 23 条 + fd-wire 根 `openspec/specs/` 45 条），代码主体在 fd-wire 仓（`api/`、`web/`、引擎与 MCP 面），部分契约面（计量、租户、身份）跨到 paas。生产部署经 fd-infra-deploy + ArgoCD（快照仓 tag=快照 sha）。子代理并行执行按本仓 AGENTS.md 偏好，最高 12 并发。

## Goals / Non-Goals

**Goals:**
- 每个模块一张可复核的健康卡，五项检查结论带证据（文件路径/命令输出），不允许无证据断言。
- 8 对跨根重叠模块给出真源裁决建议（哪根是真源、另一根处置：合并/降为指针/废弃）。
- 评分 backlog：P0（生产风险/契约漂移）/ P1（债务/测试缺口）/ P2（陈旧/卫生）。
- 体检方法本身可复制：方法学沉淀在本文件，其余线试点直接引用。

**Non-Goals:**
- 不实施任何修复；不编辑 `openspec/specs/`；不做性能调优；不改部署。
- 不新造测量设施——运行信号只用既有探针配方与现成日志/registry 面。

## Decisions

1. **簇拆分（6 簇，非 68 单粒度）**：单模块粒度并发太碎，簇内共享代码域（同一 service 目录/同一组测试），子代理上下文可复用。簇划分见 tasks.md。
2. **五项检查的取证口径**：
   - ① 对齐：spec 的 Requirement 关键行为在代码中能否指到实现入口；反向——代码显著能力无 spec 覆盖的记 shadow。
   - ② 测试：测试文件存在性 + 近期是否可定位到该模块（不强制全量跑测，跑测由集成波统一做）。
   - ③ 部署态：fd-infra-deploy 中该服务镜像 sha vs 仓 HEAD 可达性（sha 在 HEAD 祖先链上即 fresh）。
   - ④ 运行信号：memory 沉淀的探针配方（MCP 工具面实探、registry 可见性、wire liveness 双盯）+ 近期事故记录（bag-key 校验、_bench 袋键拦截等）。子代理**只读生产**，禁止任何写操作。
   - ⑤ 陈旧度：spec 文件最后实质修改时间 vs 模块代码最近活跃时间，剪刀差 >30 天标 stale。
3. **评分**：每簇健康卡对每模块给 A/B/C/D + 五项证据；跨簇汇总成 backlog 时 P0/P1/P2。裁决建议只给方案与依据，拍板留给用户。
4. **语言**：产出物用中文，与仓内既有 change 一致。

## Risks / Trade-offs

- **子代理幻觉**：对齐检查靠读码推断，可能指错入口——缓解：健康卡强制带 `file:line` 证据，集成时抽查。
- **两根 spec 语义近似但非重复**：裁决建议可能误判——缓解：重叠对裁决单列，逐对给证据链，不批量归并。
- **生产探针扰动**：只读探针也可能压到小内存服务——缓解：限既有配方、不循环轮询、失败如实记不重试。

## 方法学实测偏差（3.3 收口，供下一条线试点复用）

1. **派单时 HEAD 必须现场取**：简报写 b3798ad，六簇开工时实查 HEAD 已是 5b782f2（归档移动）。派单简报应写「以开工时 git log -1 为准」。
2. **R 根非 git 仓**：R 根 spec 时间只能用 `stat -f %Sm`（mtime），W 根用 git log——两根口径不同，健康卡需各自注明。
3. **部署态判定可脚本化**：六簇共用同一条判定（镜像 sha `git merge-base --is-ancestor` + `git diff <sha>..HEAD -- api/ web/` 为空即「部署=代码」），下轮直接写成脚本跑一次全簇共享。
4. **簇间证据要合并的裁决**（O8）应在两边健康卡都显式标注「待与对侧合并」，集成时人工合账。
5. **抽查结果**：集成时抽 3 项最重断言（O2 超额=0、三态机、landing_tab 值域）逐一对照代码，全部实锤——file:line 强制证据规则有效。
6. **并发体检踩仓况**：fd-wire 有并发会话在动 openspec（归档移动未提交），体检先行落掉了悬置移动才开工——下轮试点同样先查 `git status`。
